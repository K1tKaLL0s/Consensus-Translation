# 文件上传与结果输出区设计（2026-05-07）

日期：2026-05-07  
范围：Streamlit UI 功能增强（上传 `txt/docx/md` + 固定结果输出区）  
目标：支持用户上传文本文件并直接进入现有翻译流程，同时补齐明确可见的翻译结果展示区。

## 1. 背景与问题

当前 UI 仅支持手工输入文本，不支持文件上传；且结果主要通过页面字段查看，缺少显式“翻译结果区”，用户感知不清晰。

用户明确要求：

1. 立刻支持上传 `TXT/docx/md` 文件用于翻译。
2. UI 上提供明确的翻译结果输出部分。

## 2. 目标与非目标

### 2.1 目标

1. 新增 `txt/md/docx` 文件上传入口。
2. 上传后将整文件内容作为一次翻译输入。
3. 新增固定结果输出区，直接展示关键翻译结果。

### 2.2 非目标

1. 不实现分段逐段翻译编排。
2. 不修改后端 `run_local_job` / `run_pretrain_job` 接口。
3. 不改变 `PAGE_FIELD_MAP` 契约键名。
4. 不引入第三阶段 AI 辅助模式能力。

## 3. 方案决策

采用 A 方案（轻量直连）：

- 在 `app.py` 增加文件上传与解析。
- 上传成功后，用解析文本覆盖当前翻译输入。
- 继续复用现有按钮与工作流函数。
- 新增固定“翻译结果”区，不依赖页面字段下拉。

## 4. 设计细节

### 4.1 上传与解析

支持扩展名：`.txt` / `.md` / `.docx`

解析逻辑：

- `txt/md`：按 UTF-8 优先解码。
- `docx`：使用 `python-docx` 读取段落并拼接。

状态提示：

- 解析成功：显示文件名与字符数。
- 解析失败：显示编码/读取错误。
- 内容为空：显示“文件内容为空或不可提取”。

### 4.2 输入优先级

本轮执行时采用以下优先级：

1. 已上传并成功解析的文本（优先）
2. 文本框手工输入

### 4.3 结果输出区

新增固定区块“翻译结果”，始终可见。

本地模式显示：

- `final_text`
- `final_score`
- `needs_review`

预训练模式显示：

- `base_result.final_text`
- `validation_metrics.overall`
- `improvement_rate`

异常时显示结构化错误提示。

### 4.4 与现有契约关系

- 保留现有 `PAGE_FIELD_MAP` 与 `extract_page_data` 行为。
- 上传与结果区为新增展示层，不破坏原契约映射。

## 5. 错误处理与体验约束

1. 文件类型不支持：提示并拒绝执行。
2. 文件解码失败：提示编码错误并保留手工输入路径。
3. docx 解析失败：提示解析错误并保留手工输入路径。
4. 超大文件：给出性能提示，不做硬拦截。

## 6. 测试与验收

### 6.1 自动化测试

至少覆盖：

1. `txt/md/docx` 解析成功路径。
2. 空内容与异常路径提示。
3. 结果区关键字段展示逻辑。
4. 原有 `tests/test_ui_contract_mapping.py` 继续通过。

### 6.2 端到端验收

手工验证三类文件各一次：

1. 上传 -> 触发翻译 -> 结果区刷新。
2. 本地与预训练按钮均可执行。
3. 无需切换 page 也可看到核心输出。

### 6.3 发布门槛

1. 全量 `pytest -q` 通过。
2. 无第三阶段 AI 入口变更。
3. 后端契约字段名与接口保持不变。

## 7. 风险与控制

风险：上传解析与现有输入状态冲突。  
控制：显式优先级规则 + 状态提示。

风险：结果区与页面映射数据重复导致认知混乱。  
控制：结果区只展示“核心结果”，详细字段仍在页面映射中查看。

## 8. 完成定义

以下条件同时满足即视为完成：

1. 支持上传 `txt/md/docx` 并执行翻译。
2. UI 新增固定翻译结果区并正确显示关键字段。
3. 既有契约映射测试与全量测试通过。
