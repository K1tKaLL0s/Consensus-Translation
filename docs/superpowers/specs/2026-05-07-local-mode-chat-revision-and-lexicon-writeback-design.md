# 本地模式对话输出、容错融合与修正回写设计（2026-05-07）

日期：2026-05-07  
范围：本地模式翻译工作流 + Streamlit 主区交互  
目标：修复本地翻译易失败问题，按句子级规则融合输出，并将“用户修正 -> 词库回写”在本地模式闭环落地。

## 1. 背景与问题

当前实现存在三类发布阻断点：

1. 引擎异常（包含 `IndexError: index out of range in self`）会导致本地任务直接失败，缺少“单引擎幸存降级”。
2. 本地模式仍是候选整体二选一，不满足“按句子片段按重合度/置信度融合”的规则。
3. 主区输出仍以结构化面板为主，缺少“确认/修正”对话流程；“用户修正 -> 词库回写”尚未在本地模式完成闭环。

另据产品原始定义（`共识翻译.md` 本地模式），用户修正应在本地模式中触发差异比对、主题归档、特殊标记与词库回写。

## 2. 目标与非目标

### 2.1 目标

1. 本地翻译支持引擎级容错：单侧失败可继续输出，双侧失败才判定失败。
2. 新增句子级融合模块，输出 `final_text` 与可追踪融合原因。
3. 主区改为对话式输出：标题下仅保留对话框，不显示其他信息。
4. 在预备译文气泡提供 `确认` / `修正` 开关：
   - 选择 `确认`：直接输出最终文本。
   - 选择 `修正`：进入用户修正输入，并触发词库回写闭环。
5. 本地模式落地“用户修正 -> 词库回写”：按主题写入，差异大时打特殊标记。

### 2.2 非目标

1. 不扩展第三阶段 AI 辅助模式。
2. 不改变后端契约主键名与阶段枚举。
3. 不引入云端词库，仅处理本地词库。

## 3. 架构设计

### 3.1 融合模块抽离

新增 `src/consensus_translation/merging.py`：

- `split_sentences(text: str) -> list[str]`
- `sentence_overlap(a: str, b: str) -> float`
- `merge_sentences(a_text: str, b_text: str, a_conf: float, b_conf: float) -> MergeResult`

`MergeResult` 结构：

- `final_text: str`
- `decision_reason: str`
- `merge_trace: list[dict[str, object]]`（每句来源与判定原因）

融合规则（已确认）：

1. 按句子粒度对齐。
2. 同句位双候选存在时，优先“重合度 + 置信度”的综合判定。
3. 若仅一侧有句子，直接采用该侧。
4. 句位平局时，以更高置信度侧为准。

### 3.2 工作流容错与回写

修改 `src/consensus_translation/workflows.py`：

1. 引擎调用改为“收集失败、尽可能继续”：
   - A 成功/B失败：继续。
   - B 成功/A失败：继续。
   - A、B都失败：抛错并保留结构化错误信息。
2. 成功路径：
   - 双成功：走 `merge_sentences`。
   - 单成功：直接取幸存候选并设置 `engine-single-survivor-*` 决策原因。
3. 在结果中新增可观测字段：
   - `merge_trace`
   - `engine_errors`
   - `provisional_text`（预备结果）
4. 新增本地修正回写入口函数（建议）：
   - `apply_local_revision(...) -> dict[str, object]`
   - 输入：原文、预备译文、用户修正、topic
   - 输出：`diff_ratio`、`special_flag`、`update_status`、`lexicon_updates`

### 3.3 词库回写规则（本地模式）

基于 `LexiconRepo` 落地以下约束：

1. 仅当用户点击 `修正` 并提交修正文本时触发回写。
2. 主题为空时统一落 `uncategorized`。
3. 先计算 `diff_ratio`，再决定特殊标记（阈值沿用现有规则：`>= 0.6`）。
4. 回写至少覆盖 `terms`；`phrases` / `style_rules` 由规则提取后写入（若未识别则保持空层，不阻塞主流程）。
5. 回写失败不覆盖已有翻译结果，但必须在状态字段暴露失败原因。

## 4. UI 交互设计（主区）

修改 `app.py` 主区行为：

1. 标题下仅显示对话流，不再渲染 JSON 结果面板。
2. 翻译完成后先输出 assistant 气泡（预备译文文本）。
3. 同轮提供按钮：`确认` / `修正`。
4. 点击 `确认`：直接将当前预备译文定稿并结束本轮。
5. 点击 `修正`：
   - 启用底部 `chat_input`。
   - 用户输入以 user 气泡显示。
   - 触发回写并输出 assistant 气泡（修正后文本）。
6. 双引擎失败时，仅输出 assistant 气泡：`翻译失败`。
7. 技术细节（如 `engine_errors`、回写失败信息）仅放侧栏状态，不进入主对话区。

## 5. 测试策略（TDD）

### 5.1 工作流测试

在 `tests/test_workflows.py` 新增用例：

1. 单引擎 `IndexError` 触发降级，仍产出 `final_text`。
2. 双引擎失败时结构化错误仍可观测。
3. 句子级融合符合“重合+置信”规则。
4. 本地修正触发回写：
   - `update_status` 成功
   - 主题落库正确
   - `diff_ratio >= 0.6` 时 `special_flag=True`

### 5.2 UI 测试

在 `tests/test_ui_contract_mapping.py` 新增用例：

1. 主区不再依赖 `build_result_panel` JSON 展示。
2. 存在确认/修正分支状态键（确认不回写、修正才回写）。
3. 修正文本进入对话历史并触发回写状态更新。

## 6. 风险与缓解

1. 风险：句子对齐偏差导致融合不自然。  
   缓解：采用稳定分句 + 置信度兜底，记录 `merge_trace` 便于回溯。

2. 风险：回写失败影响用户观感。  
   缓解：翻译结果与回写结果解耦；回写失败仅写状态，不阻断主输出。

3. 风险：UI 交互状态复杂导致分支遗漏。  
   缓解：为“确认/修正”分别补最小状态机测试。

## 7. 完成定义

以下条件同时满足视为完成：

1. `IndexError` 单侧异常不再导致整体失败。
2. 本地模式输出改为句子级融合结果。
3. 标题下主区仅有对话框文本流。
4. 仅在选择 `修正` 后触发“用户修正 -> 词库回写”。
5. 相关自动化测试通过且覆盖核心分支。
